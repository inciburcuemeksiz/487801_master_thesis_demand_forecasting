# Demand Forecasting Ensemble — Frontend & Backend Guide

This document explains how the Gradio frontend (`app.py`) connects to the machine
learning backend (`build_artifacts.py`), what data flows between them, and how to
run the full system locally.

---

## Project Structure

```
demand_forecasting/
    app.py                    # Gradio UI — the frontend
    build_artifacts.py        # ML pipeline — the backend
    generate_mock_data.py     # Generates mock_orders.csv for testing
    mock_orders.csv           # Mock orders data (generated, not real)
    model_artifacts.pkl       # Serialised ML outputs consumed by app.py
    forecast_trial_1.ipynb    # Original Colab notebook (reference only)
    requirements.txt          # Python dependencies
```

---

## How the System Works

The frontend and backend are decoupled. They communicate through a single file:
`model_artifacts.pkl`.

```
build_artifacts.py  -->  model_artifacts.pkl  -->  app.py
   (run once)               (on disk)              (runs anytime)
```

The ML engineer runs `build_artifacts.py` once with real order data. This trains
the propensity model and saves the results to disk. From that point on, the
product manager can open `app.py`, type in any new product, click
"Generate Forecast", and get an instant result.

Each click runs the full forecast calculation live: the app matches the new
product against historical SKUs, applies the price and seasonal multipliers,
scores the customer base using the pre-trained propensity scores, and blends
the three models into a final unit forecast. Results appear in seconds because
the slow part — training the model on thousands of customer records — was
already done by `build_artifacts.py` and does not repeat on every click.

The pkl file only needs to be regenerated by the ML engineer when the
underlying order data or the launch reference table changes.

## Step 1 — Backend: build_artifacts.py

### What it does

Reads a raw orders CSV and runs the full ML pipeline in 9 steps:

1. Load the CSV and anonymise customer emails via SHA-256 hashing
2. Explode product and quantity lists into one row per product line
3. Tag each transaction with its sale period (if any)
4. Compute product category flags: health, hydration, protein, co-creation
5. Build the hardcoded launch performance reference table (`launch_perf_df`)
6. Derive two data-driven coefficients from the launch table:
   - `price_elasticity` — log-log regression of price vs. units sold
   - `influencer_uplift_factor` — average units of CoCreation launches vs. standard
7. Build a customer-level feature table (RFM + affinity scores per customer)
8. Train a `HistGradientBoostingClassifier` propensity model and score all customers
9. Compute `hydration_momentum` — ratio of recent 4-week vs. 12-week hydration sales

### What it saves

All outputs are serialised into `model_artifacts.pkl` as a Python dictionary:

| Key | Type | Description |
|-----|------|-------------|
| `launch_perf_df` | DataFrame | 22-row reference table of historical launches with price, units, target group |
| `feature_table` | DataFrame | One row per customer with RFM, affinity scores, and `p_buy_model2` propensity |
| `auc` | float | AUC score of the propensity model on the held-out test set |
| `price_elasticity` | float | Slope from log-log regression (price vs. quantity) |
| `influencer_uplift_factor` | float | Co-creation uplift multiplier derived from launch history |
| `hydration_momentum` | float | Trend ratio: avg weekly units last 4 weeks / last 12 weeks |

### How to run

```bash
source .venv/bin/activate
python build_artifacts.py --csv path/to/orders.csv
```

For testing without real data:

```bash
python generate_mock_data.py          # creates mock_orders.csv
python build_artifacts.py --csv mock_orders.csv
```

### Expected CSV schema

The input CSV must have these columns:

| Column | Description |
|--------|-------------|
| `customer_email` | Raw email — hashed and dropped immediately |
| `customer_status` | `new` or `returning` |
| `order_date` | Date string, e.g. `2025-04-22` |
| `order_id` | Unique order identifier |
| `product_list` | Comma-separated product names, e.g. `Vegan Protein Pulver - Cookie Dough,Hydrate Drink - Lemon` |
| `quantity_list` | Comma-separated integers matching product_list length, e.g. `2,1` |
| `net_revenue` | Order-level revenue as a float |
| `coupon_code` | Applied coupon code or empty |
| `coupon_influencer` | Influencer handle linked to coupon, e.g. `fit_laura`, or empty |

## Step 2 — Frontend: app.py

### What it does

Loads `model_artifacts.pkl` once at startup, then runs a Gradio web interface
where the user fills in a new product profile and receives a demand forecast.

### How to run

```bash
source .venv/bin/activate
python app.py
```

Opens at `http://127.0.0.1:7860` (or next available port).

### Input fields

| Field | Type | Description |
|-------|------|-------------|
| Product Name | Text | Free-text name of the new product being evaluated |
| Characteristics | Text | Comma-separated product attributes, e.g. `HIGH PROTEIN, VEGAN, COCONUT` |
| Key Search Terms | Text | Keywords used to find the nearest historical SKUs |
| Unit Price (EUR) | Number | Planned retail price — fed into the price elasticity calculation |
| Month Index | Dropdown | Launch month — maps to a seasonal index multiplier |
| Collaboration Mode | Radio | `Co-Creation` applies the influencer uplift factor; `Standard` sets it to 1.0 |

### How a forecast is calculated

When the user clicks "Generate Forecast", the following happens:

**1. Nearest-SKU matching**

The characteristics and search terms are tokenised into keywords. Each row in
`launch_perf_df` is scored by how many keywords appear in its name, flavour, and
target group fields. The top 5 matching SKUs become the reference set for Model 1.

**2. Dynamic factors**

Three multipliers are computed from the user inputs:

- `seasonal_factor` — looked up from a hardcoded monthly index (Nov = 1.30, Dec = 0.75, etc.)
- `dyn_price_factor` — `(unit_price / avg_catalogue_price) ^ price_elasticity`
- `dyn_inf_factor` — `influencer_uplift_factor` if Co-Creation, else `1.0`

**3. Three models**

- Model 1 (Baseline): average `total_quantity` of the 5 nearest SKUs, multiplied by all three dynamic factors
- Model 2 (Propensity): sum of `p_buy_model2` scores across all customers in `feature_table`, re-scaled by the dynamic factors
- Model 3 (Scenario): Model 2 total further multiplied by `hydration_momentum`, representing a trend-adjusted scenario

**4. Blended ensemble**

```
final = 0.50 * Model1 + 0.30 * Model2 + 0.20 * Model3
```

**5. New customer projection**

Filters `feature_table` to rows where `is_new_customer == 1`, sums their
`p_buy_model2` scores (re-scaled), and rounds to an integer.

### Outputs

| Output | Description |
|--------|-------------|
| Estimate. Blended Volume | Final rounded integer unit forecast |
| New Customer Proj. | Projected units from new customers only |
| Ensemble Comparison Chart | Plotly bar chart comparing the three models and the blended result, with a confidence score |
| Process Telemetry | Timestamped log of each computation step |
| Model Reference Set | Table of the 5 nearest matched SKUs with their volume deviation from the catalogue average |

## Notes for the ML Engineer

- The model currently uses `HistGradientBoostingClassifier` from scikit-learn as a
  drop-in replacement for XGBoost. XGBoost requires `libomp` on macOS, which needs
  admin access to install via Homebrew. If you are on Linux or have Homebrew
  available, XGBoost can be swapped back in `build_artifacts.py` — the interface
  is identical (`fit`, `predict_proba`).

- The label used to train the propensity model is `label_prev_cocreated`, a binary
  flag indicating whether a customer has ever purchased a co-created product (Vegan
  Protein Pulver Cookie variants). This acts as a proxy for co-creation affinity.
  If you want to retrain for a different product category, update that label
  definition in `build_artifacts.py` step 8.

- `launch_perf_df` is currently hardcoded in both `build_artifacts.py` and the
  notebook. If the launch table grows, it should be extracted into a separate CSV
  and loaded by both files.

- `model_artifacts.pkl` must be regenerated every time the training data or the
  launch reference table changes. The frontend does not retrain — it only reads
  the pkl file.
